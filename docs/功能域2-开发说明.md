## 一、这个域做了什么

功能域2负责整个拼车系统的**订单核心**，包括：

- 乘客发布订单（选路线、时间、座位需求、标签偏好）
- 其他用户搜索/浏览可拼订单
- 车主选择自己的车辆接单，锁定行程
- 行程结束后标记完成
- 管理员可强制取消任何订单
- 车主名下车辆信息的查询、登记、编辑、启停和车辆认证
- 车牌号规范检测、车辆型号输入联想
- 车辆认证审核中状态展示和重复提交拦截

简单说：**从订单发布到订单完成的全生命周期**，都在这个域里。

> **当前状态**：功能已初步完成，可运行全流程测试。Mock 模式下无需数据库，切换真实 MySQL 需额外配置（见第七节）。

## 二、用户能看到什么界面

### 乘客视角

| 页面 | 访问路径 | 能做什么 |
|------|----------|---------|
| 乘客首页 | `/passenger/home` | 快速进入搜索、查看自己的订单、看到近期记录 |
| 发布订单 | `/passenger/orders/publish` | 填写出发地/目的地（有输入建议）、出发时间窗口、同行人数、期望车费、选择标签 |
| 搜索订单 | `/passenger/orders/search` | 按路线/时间/标签筛选招募中的订单，点击卡片查看详情 |
| 我的订单 | `/passenger/orders/mine` | 查看自己发布的全部订单，按状态 tab 切换 |
| 订单详情 | `/passenger/orders/:id` | 查看完整信息、参与拼单、取消订单 |

**发布订单页功能亮点：**
- 输入出发地/目的地时会弹出预置地点建议（可输入关键词过滤）
- `我方人数`（含本人）+ `还能带几人` 合并计算"共占座位"
- 实时显示"每人均价"（= 期望总价 ÷ 总人数）
- 标签分为预置标签（点击选中/取消）和自定义标签（输入后回车/点 + 添加）

### 车主视角

| 页面 | 访问路径 | 能做什么 |
|------|----------|---------|
| 车主首页 | `/driver/home` | 看到待接订单数、进行中订单数，快速跳转 |
| 可接订单 | `/driver/orders/available` | 浏览所有招募中的订单，点"接单"弹出车辆选择 |
| 我的接单 | `/driver/orders/mine` | 查看自己已接的订单，locked 状态可标记完成或取消 |
| 我的车辆 | `/me/vehicles` | 查看车辆状态、认证状态，可编辑、启停、删除或发起认证 |
| 新增车辆 | `/me/vehicles/create` | 登记车辆，车牌号实时校验，车型输入支持联想 |
| 车辆认证 | `/me/vehicles/:vehicleId/verify` | 提交车辆认证资料，审核中车辆无法重复提交 |

**接单流程：**
1. 在"可接订单"列表里找到合适的订单
2. 点"接单 →"，弹出底部弹窗
3. 从自己名下车辆列表选择一辆（自动拉取，只有一辆时自动选中）
4. 点"确认接单"，订单状态变为 `locked`

> 接单时后端会再次强校验车辆：必须是本人车辆，且车辆已通过认证、未禁用。即使用户已经具备车主资格，也不能使用未认证、审核中、禁用或非本人车辆接单。

| 订单管理 | `/admin/orders` | 查看全部订单，按关键词搜索，按状态筛选，强制取消任意未完成订单 |

## 三、后端：10个接口详解

服务地址（本地）：通过网关 `http://localhost:8000` 访问，实际由 8002 端口的订单域处理。

### 接口鉴权约定

所有接口通过 HTTP Header 传递用户身份（无 JWT，符合课设约定）：

```
X-User-Id: dev-user-1        # 当前用户的 userId
X-User-Role: admin           # 仅管理员操作时附加
X-Owner-Verified: true       # 车辆管理、车辆认证和车主接单时需要
```

> 车主资格由账号域登录结果提供，前端只读取后端返回的 `ownerVerified` / `userId` 并透传到订单域，不在登录域内硬编码判断逻辑。

---

### 接口1：发布订单

```
POST /api/orders
```

**请求示例**：
```json
{
  "start_loc": "软件园",
  "end_loc": "大学城",
  "depart_time_from": "2026-04-15T08:00:00",
  "depart_time_to": "2026-04-15T09:00:00",
  "group_size": 2,
  "extra_seats": 1,
  "expected_price": 45.0,
  "tags": ["静音", "禁烟"]
}
```

字段说明：
- `group_size`：本人一行几人（含本人），最少为 1
- `extra_seats`：还能再带几个陌生人上车，0 表示不拼其他人
- 系统计算 `seats_needed = group_size + extra_seats`（总座位需求）

**成功响应**：
```json
{ "order_id": "ord-xxxxxxxx", "status": "published" }
```

---

### 接口2：搜索订单

```
GET /api/orders/search?start_loc=南门&tags=静音
```

**查询参数**（全部可选，不传则不限制该条件）：

| 参数 | 说明 | 示例 |
|------|------|------|
| `start_loc` | 出发地关键词（模糊匹配） | `南` 可匹配"南门"、"南区" |
| `end_loc` | 目的地关键词（模糊匹配） | |
| `time_from` | 出发时间下限 | `2026-04-15T08:00:00` |
| `time_to` | 出发时间上限 | |
| `tags` | 标签筛选，逗号分隔，**需全部命中** | `静音,禁烟` |

> 只返回状态为 `published` 或 `full` 的订单（招募中）

**响应**：返回订单列表，每条订单包含 `remaining_seats`（剩余可拼座位数）

---

### 接口3：订单列表

```
GET /api/orders?passenger_id=dev-user-1
GET /api/orders?owner_id=dev-user-1
GET /api/orders                          ← 管理员用，返回全部
```

---

### 接口4：订单详情

```
GET /api/orders/{order_id}
```

返回单条订单的完整信息，包括 `locked_time`（车主接单时间）、`vehicle_id` 等。

**错误码**：`404`（订单不存在）

---

### 接口5：修改订单

```
PUT /api/orders/{order_id}
```

**限制**：只有发单人本人，且订单处于 `published` 状态时才能修改。

**错误码**：`403`（非本人）、`409`（状态不允许修改）

---

### 接口6：取消订单

```
POST /api/orders/{order_id}/cancel
```

**谁可以取消**：
- 发单人（乘客）本人
- 已接单的车主
- 已参与拼单的其他乘客
- **管理员**（附加 `X-User-Role: admin` header）

> 如果订单处于 `locked` 状态时取消，响应中 `penalty: true`，表示需要扣除信誉积分（积分扣除由功能域3处理，本域只标记结果）

**错误码**：`403`（无权限）、`409`（订单已结束）

---

### 接口7：乘客拼单（加入订单）

```
POST /api/orders/{order_id}/join
```

**场景**：发单人发的订单有空余座位，其他乘客想一起拼，点"参与拼单"。

> 座位满时订单状态自动从 `published` 变为 `full`

**错误码**：`409`（已参与 / 已满员 / 状态不允许）

---

### 接口8：车主接单

```
POST /api/orders/{order_id}/accept
Body: { "vehicle_id": "veh-001" }
```

车主选择用哪辆车接单，订单状态变为 `locked`，同时记录 `owner_id`、`vehicle_id`、`locked_time`。

**接单限制**：
- 请求头必须包含 `X-Owner-Verified: true`
- 订单必须处于 `published` 或 `full` 状态
- 车辆必须归当前用户所有
- 车辆必须已通过认证，且 `status=available`

**错误码**：`403`（未完成车主认证 / 非本人车辆）、`409`（已被接单 / 状态不允许 / 车辆未认证或被禁用）

---

### 接口9：标记完成

```
POST /api/orders/{order_id}/complete
Body: { "operator": "driver" }    ← 车主手动完成
Body: { "operator": "domain3" }   ← 支付完成后由功能域3回调
```

订单状态从 `locked` 变为 `completed`。

**错误码**：`409`（订单未处于 locked 状态）

---

### 接口10：查询车辆列表

```
GET /api/vehicles
Header: X-User-Id: dev-user-1
```

返回该车主名下全部车辆，用于接单时选车。

车辆列表会返回 `verified`、`verify_status`、`status` 等字段，用于前端展示车辆是否可接单、是否正在审核。

| 字段 | 说明 |
|------|------|
| `verified` | 是否已通过车辆认证 |
| `verify_status` | `unsubmitted` 未提交、`pending` 审核中、`approved` 已通过 |
| `status` | `available` 可用、`disabled` 已禁用 |

### 车辆管理接口补充

车辆管理接口均要求当前用户已完成车主身份认证：

| 接口 | 说明 | 关键校验 |
|------|------|----------|
| `POST /api/vehicles` | 新增车辆 | 车牌号必须符合规范，同一车牌不可重复登记 |
| `PUT /api/vehicles/{vehicle_id}` | 编辑车辆 | 只能编辑本人车辆，车牌号继续校验规范 |
| `PATCH /api/vehicles/{vehicle_id}/status` | 启用/禁用车辆 | 只能切换本人车辆，禁用后不可用于接单 |
| `DELETE /api/vehicles/{vehicle_id}` | 删除车辆 | 只能删除本人车辆 |
| `POST /api/vehicles/{vehicle_id}/verify-request` | 提交车辆认证 | 已有 `pending` 申请时返回"该车辆认证正在审核"，禁止重复提交 |

## 五、订单状态流转图

```
                  ┌─────────────────────────────────────────┐
                  │                                         │
         发布订单 ▼                                         │
           ┌──────────┐   座位满员      ┌──────────┐       │
           │published │ ─────────────▶ │  full    │       │
           │ (招募中) │ ◀────────────── │ (已满员) │       │
           └────┬─────┘   有人退出      └──────────┘       │
                │                                         │
                │ 车主接单（选车辆）                         │
                ▼                                         │
           ┌──────────┐   标记完成    ┌───────────┐       │
           │  locked  │ ────────────▶ │ completed │       │
           │ (已锁单) │              │ (已完成)  │       │
           └──────────┘              └───────────┘       │
                │                                         │
                │ 取消（发单人/车主/乘客/管理员）            │
                ▼                                         │
           ┌──────────┐                                   │
           │cancelled │ ◀─────────────────────────────────┘
           │ (已取消) │   （published/full/locked 均可取消）
           └──────────┘
```

| 状态 | 中文 | 颜色标识 | 说明 |
|------|------|----------|------|
| `published` | 招募中 | 蓝色 | 可被搜索、可接单、可拼单 |
| `full` | 已满员 | 黄色 | 座位满了，不再接受新乘客 |
| `locked` | 已锁单 | 橙色 | 车主已接单，等待出发 |
| `completed` | 已完成 | 绿色 | 行程结束 |
| `cancelled` | 已取消 | 灰色 | 已取消，信誉积分可能扣除 |

## 七、如何在本地启动

## 八、与其他功能域的对接方式

### 对功能域1（账号域 · wyx）

**本域需要账号域提供的信息：**

用户登录成功后，账号域需要将以下信息写入 `localStorage`：

```javascript
localStorage.setItem('session', JSON.stringify({
  userId: 'user-001',   // 用户唯一ID（字符串）
  role: 'passenger',    // 'passenger' | 'driver' | 'admin'
  username: 'alice'     // 显示名称（可选）
}))
```

本域读取 `userId` 作为 `X-User-Id` header，读取 `role` 决定显示哪个 Tab（乘客/车主/管理员）。

> ⚠️ `role` 字段必须是以上三个值之一，否则底部导航栏无法正确显示。如果账号域用的字段名不同，告知 hws 调整映射。

**本域不依赖账号域的接口**，不会调用 `/api/auth/*`。

---

### 对功能域3（交易域 · yzr）

**功能域3可以调用本域的接口：**

1. **订单完成回调**：支付成功后，域3调用以下接口将订单标记为完成：
   ```
   POST /api/orders/{order_id}/complete
   Header: X-User-Id: {domain3-service-id}
   Body: { "operator": "domain3" }
   ```

2. **查询订单金额**：域3计算拆单金额时，通过订单详情接口获取 `expected_price` 和 `seats_needed`：
   ```
   GET /api/orders/{order_id}
   ```
   每人应付 = `expected_price ÷ seats_needed`（前端用相同逻辑显示每人均价）

**本域不调用功能域3的接口**，不处理支付流程。

## 九、对原框架的修改说明

本节说明相对于初始框架（`init` commit）做了哪些修改，以及原因。

### 后端

| 文件 | 原框架状态 | 本次改动 |

## 十一、常见问题 FAQ

**Q: 启动时提示端口被占用怎么办？**

先查是谁占了：
```bash
netstat -ano | findstr :8002
```
如果是之前的 Python 进程没退出，Ctrl+C 关掉或任务管理器结束 Python 进程即可。

---

**Q: 切换角色后页面乱了怎么办？**

点"退出登录"彻底清空 session 后重新选角色，或者在 Chrome 开发者工具 → Application → Local Storage 里删除 `session` 键。

---

**Q: Mock 模式下数据会消失？**

是的，Mock 用内存存储，重启服务后重置。**2026-04-23 起默认已切换为真实数据库模式**（`RIDE_USE_MOCK=false`），需要本地有 MySQL 并执行初始化脚本（见第十二节）。如需临时使用 Mock，在 `.env` 里设置 `RIDE_USE_MOCK=true` 即可。

---

**Q: 功能域3怎么知道一笔订单完成了？**

两种方案：
- **推荐**：支付成功后，域3主动调用 `POST /api/orders/{id}/complete`，body 传 `{"operator": "domain3"}`
- 备选：域3轮询 `GET /api/orders/{id}` 查询状态

#### 本地数据库初始化步骤

```bash
# 在 MySQL 中按顺序执行（以 Docker 为例）
docker exec -i <容器名> mysql -u root -p<密码> < sql/ride/001_init.sql

```
RIDE_DB_HOST=127.0.0.1

RIDE_DB_USER=root
RIDE_DB_PASSWORD=<你的密码>

## 十四、2026-05-07 更新说明

本次更新补齐车主资格、车辆认证和车辆接单的状态一致性，重点保证"能看到的状态"和"后端真正允许的操作"保持一致。

### 主要变更

#### 车主身份与车辆管理门禁

- 车辆管理相关页面增加 `ownerRequired` 路由门禁，未完成车主身份认证的用户会被引导先完成车主认证。
- 车辆管理和车主接单接口统一携带 `X-Owner-Verified`，后端据此拦截未具备车主资格的请求。
- 个人中心在用户已具备车主资格时不再继续展示重复认证入口，并用更清晰的状态卡展示"已具备车主资格"。

#### 车牌号校验与车型联想

- 新增车辆和编辑车辆时，车牌号需要通过规范校验，避免出现明显不合规的车牌号。
- 车辆型号输入框支持单字触发联想，并扩充了常见车型候选，方便测试和录入。

#### 车辆认证审核中状态

- 车辆认证提交后会进入 `pending` 审核中状态。
- 认证选择界面遇到 `pending` 车辆时显示"该车辆认证正在审核"，并禁止重复提交新的认证。
- 车辆列表同步展示"车辆认证审核中"状态，避免列表仍显示"可接单"造成误导。

#### 接单强校验

- 车主接单时继续强校验车辆归属、车辆认证状态和车辆启停状态。
- 即使车主身份认证通过，也不能使用未认证、审核中、禁用或非本人车辆接单。
- 车辆列表、接单弹窗和后端校验现在使用同一套状态口径：只有 `verified=true` 且 `status=available` 的本人车辆才可接单。
