# Software-project
软件工程课设-手机私家车拼车软件（V1）

python版本：3.9

+Vue3

## 1. V1实现功能：

1. 注册时一个账号：默认是拼车人，在个人中心额外认证车主。
2. 订单规则：拼车人发布订单，车主只能接单，不能发布订单。
3. 标签功能：拼车人发布订单时可选择标签（例如：“宠物友好”、“静音”、“禁烟”等）。
4. 管理端：管理员账号内置在数据库，不能注册获得管理员权限。
5. 安全保障、评价机制放到V2。


车主

（1）车主注册、登录

（2）车主发布车辆信息

（3）接拼车单（车主浏览拼车信息发布界面，选择接单）

（4）收款提现

（5）反馈互动

拼车人

（1）拼车人注册、登录

（2）拼车人发布拼车订单

（3）接受拼车邀请（拼车人浏览拼车信息发布界面，选择拼单）

（4）搜索拼车订单

（5）支付订单

【不用真正接微信/支付宝的付款，模拟支付即可】

（6）互动反馈

管理员

（1）管理员登录

【数据库内置管理员账号密码，不能通过注册获得管理员权限】

（2）用户账号管理

（3）拼车订单管理

（4）反馈信息管理

## 2. 功能域划分
三个数据库：

**account_db**（用户、车主认证、管理员账号）

+**ride_db**（订单+车辆）。【订单和车辆信息就建立在一个库里，因为当前场景车辆信息与订单信息是强一致高耦合关系，拆开成两个库可能增加了分布式管理的复杂度】

+**ops_db**（支付、钱包、反馈、运营管理）

### 功能域1：账号与身份域（1人）
wyx
功能范围：

1. 用户注册、登录（注册时默认是拼车人身份，车主身份需要在个人中心额外认证）。
2. 个人中心页面（车主认证后可以看到自己名下的车辆信息）与状态管理（停用/可用）。
3. 车主身份认证管理（申请/审核状态）。
4. 管理员登录（数据库建表时内置管理员）
4. 拼车人/车主身份独立停用（低信誉积分的拼车人/车主账号停用。之前有说拼车人/车主共用一个账号，两个身份的信誉积分是独立的，每次只停用一个身份的账号功能）。

不负责（避免耦合）：

1. 不维护订单状态。
2. 不维护钱包余额和支付流水。

涉及数据库：`account_db`（用户、车主认证、管理员账号）。

### 功能域2：订单与车辆（2人）
hws、zj
功能范围：

1. 车主认证通过后维护车辆信息（车辆增删改查、可用状态）。
2. 拼车人发布订单（发布订单时可以个性化设置标签）。
3. 拼车人查看自己已发布订单。
4. 订单搜索（根据目的地、出发地、出发时间段等条件筛选搜索）、查看订单详情。
5. 车主接单、其他拼车人确认参与拼单。（车主一旦接单后，拼车人/车主取消订单都需要扣除一定的信誉积分）
6. 订单主状态流转（已发布-> 司机接单、其他拼车人确认拼车 -> 出发前预支付车费（参与拼单的人a钱） -> 订单结束）。

不负责（避免耦合）：

1. 不做登录认证规则判断（依赖数据库返回身份结果）。
2. 不做支付扣款、提现入账。

数据归属：`ride_db`（订单+车辆）。【订单和车辆信息就建立在一个库里，因为当前场景车辆信息与订单信息是强一致高耦合关系，拆开成两个库可能增加了分布式管理的复杂度】

### 功能域3：交易流转（1人）
yzr
功能范围：

1. 拼车人模拟支付（每个人支付金额的计算、行程费用的计算）模拟支付、支付单状态、退款。
2. 钱包余额、提现申请、流水记录。
3. 反馈/投诉与管理员处理。
4. 用户反馈与管理员反馈处理（拼车人和车主之间即时的信息交流、拼车人/车主向管理方发起投诉->管理员介入）。

不负责（避免耦合）：

1. 不直接改订单主状态（仅通过功能域2开放接口回写支付结果）。
2. 不直接修改用户身份基础资料（调用功能域1管理接口）。

涉及数据库：`ops_db`（支付、钱包、反馈、运营管理）。

### ！！约束！！

1. 仅通过API通信，不允许跨服务直连数据库。
2. 跨域只保存外键ID和必要快照，不复制完整数据库对象。
3. 任何跨域写操作必须通过对方服务接口完成。
4. `account_db`/`ride_db`/`ops_db`各有唯一Owner，其他成员禁止直接改表结构。
5. 用户身份统一由功能1提供，其他服务仅存userId。
6. 订单主状态只允许功能2维护。
7. 钱包余额与支付流水只允许功能3维护。
